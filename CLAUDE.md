# CLAUDE.md

Architecture reference for **JoJo: Steel Ball Crusaders**, a Roblox multiplayer game built with Rojo. Read this before making non-trivial changes — the codebase has several sharp edges (duplicated logic, dead code, no central remote registry) that are easy to trip over if you assume a cleaner architecture than what actually exists.

## Project / Rojo layout

`default.project.json` maps:

| Source dir | Roblox destination |
|---|---|
| `src/shared` | `ReplicatedStorage.Shared` |
| `src/server` | `ServerScriptService` |
| `src/client` | `StarterPlayer.StarterPlayerScripts` |
| `src/clientchar` | `StarterPlayer.StarterCharacterScripts` |

**File-suffix convention overrides folder location.** Rojo decides script type from the filename suffix, not the parent container:
- `*.server.luau` → `Script` (runs server-side) regardless of where it sits
- `*.client.luau` → `LocalScript` (runs client-side) regardless of where it sits
- `*.luau` (no suffix) → `ModuleScript`

This is why `src/clientchar/Health.server.luau` and `Ragdoll.server.luau` are real server `Script`s even though `src/clientchar` maps to `StarterCharacterScripts` — they get cloned into each character model and run with server authority per-character (standard Roblox pattern, mirrors the stock `Health`/`Animate` scripts). Similarly, everything under `src/shared/StandLocalScripts/**` and `src/shared/SpecialtyLocalScripts/**` is `.client.luau` sitting in `ReplicatedStorage.Shared` — inert there, and only runs once something (`src/server/Utilities/GiveLocalScripts.server.luau`) clones it into a player's scripts. **When adding a script, name it for how it should run, not where you put it.**

Toolchain: Rojo 7.5.1, Wally 0.3.2 (managed via Rokit; `wally.toml` currently has **no external dependencies** — nothing is actually pulled from the Wally registry). Selene lint config is minimal (`std = "roblox"` only). StyLua is the formatter of record (`.vscode/settings.json`), default style, no `.stylua.toml`. `sourcemap.json` is generated by Rojo — never hand-edit it.

## Player data & persistence

- **`src/server/DataSaving/ProfileStore.luau`** — vendored copy of the MadStudio "ProfileStore" library. Session-locking DataStore wrapper; store name is `"Production"` or `"Test"` depending on `RunService:IsStudio()`.
- **`src/server/DataSaving/PlayerData.luau`** — the real entry point. Instantiates the store with `ProfileStore.New(DATA_STORE_KEY, PlayerDataTemplate.DEFAULT_PLAYER_DATA)`. Profile key = `tostring(player.UserId)`. On join: `StartSessionAsync` → kick on failure → `AddUserId` + `Reconcile()` to backfill new template fields → `OnSessionEnd` kicks on session steal. This module is also the **only bridge** between ProfileStore and the in-memory gameplay systems (see below) — it hand-copies fields field-by-field in `Local.LoadProfile`, `Local.RemoveProfile`, and `PlayerData.SafeSwitchSlot` (three near-duplicate copy blocks; if you add a new persisted field, you must update all three or it silently won't save/load).
- **`src/shared/Modules/PlayerData.luau`** — defines `DEFAULT_PLAYER_DATA`, the actual schema: `Slots`, `CurrentSlot`, `Cash`, `XP`, `Level`, `TalentPoints`, `MaxXP`, `Hero`, `Race`, `Specialty`, `UpgradeData`, `Inventory`, `Quests`, `CompletedQuests`, `CharacterUpgrades`, `DailyCodes`, `UnlockedAbilities`, `AbilityPoints`, `XPBoostExpiry` (account-wide), `PurchaseHistory` (receipt idempotency).
- **Character slots**: `src/server/DataSaving/SlotManager.luau` — up to 3 slots per profile (`Slot1` free, `Slot2`/`Slot3` gated by hardcoded gamepass IDs). Each slot is effectively a full separate character/loadout (own Hero/Race/Specialty/XP/Level/Cash/Inventory/Quests/Talents). Switching goes through `SwitchSlot` remote → `PlayerData.SafeSwitchSlot`.
- **Gameplay systems keep their own in-memory state**, keyed by `Player`/`UserId`, separate from `profile.Data`: `HeroManager`, `CashSystem`, `XPSystem`, `InventoryManager`, `TalentsModule`, `QuestManager`. Each exposes `Get/SetField` or `Get/SetStats` accessors. `profile.Data` is only synced at load/save/slot-switch boundaries via `PlayerData.luau`. **Most code reads/writes the subsystem modules directly, not `PlayerData`'s thin external API** — know which one you're touching.
- **Dead/legacy code to be aware of (don't build on these):** `src/server/DataSaving/DataStoreManager.luau` (unused legacy raw-DataStore wrapper, not ProfileStore, required nowhere), `src/server/DataSaving/PlayerProfile.luau` (stale duplicate schema, unused), `src/server/DataSaving/Test.server.luau` (2 lines, no-op).
- `SettingsSaver.server.luau` (music settings) uses its own separate DataStore entirely outside ProfileStore.

## RemoteEvents / RemoteFunctions

**There is no central remote registry.** ~70+ server scripts create Remotes ad-hoc via `Instance.new("RemoteEvent"/"RemoteFunction")` and drop them into ReplicatedStorage at runtime under inconsistently-named folders:

- `ReplicatedStorage.UIs.RemoteEvents` — biggest bucket: hero data, XP, talents, inventory, damage numbers, cooldowns
- `ReplicatedStorage.Shared.Events` — used for **two unrelated domains** (combat VFX like `SpawnVfx`/`StandAurasEvent`, *and* `SwitchSlot`/`CheckSlotAccess` — same folder name, different purpose, watch for collisions)
- `ReplicatedStorage.Shared.BasicCombat.UI` — cooldown/barrier state events
- `ReplicatedStorage.QuestEvents` — quest sync
- `ReplicatedStorage.MusicEvents` — music/settings
- `ReplicatedStorage` root — a few remotes live directly here (`TradeSubmitted`, `ControlPointCreated`)
- `ReplicatedStorage.Shared.BasicCombat.<StandName>` — legacy per-ability remotes (mostly superseded, see Stands section)
- `ReplicatedStorage.Bindables` — client-only `BindableEvent`s (menu open/close)

Every consumer re-derives remotes via hardcoded `WaitForChild` string paths — no shared enum/constants module. **If you rename a remote, grep the whole repo**; nothing will catch it at compile time, and a typo just hangs on `WaitForChild`. Some creators guard with `FindFirstChild(...) or Instance.new(...)`, others don't — load-order changes could duplicate a remote.

No consistent request/response convention: some pulls use `RemoteFunction:InvokeServer()` (`GetHeroData`, `GetHeroFunction`), others use a `RemoteEvent` request + a separate `...Updated` push-back event (`RequestXPData`/`XPUpdatedEvent`), and at least one (`TalentsRemoteHandler.server.luau`) reuses a single RemoteEvent bidirectionally as both the client's request and the server's ack. Server-side argument validation is inconsistent — present in some slot/talent handlers, largely absent elsewhere (combat/ability remotes generally trust client-supplied targets/positions and rely on server-side game logic to bound the effect, rather than validating inputs up front).

Push patterns you'll see repeated: one-shot pull (`InvokeServer`), event-driven push on state change (`HeroUpdated` → full UI reload), and polling broadcast loops (`QuestArrowAssist.server.luau` fires `SetArrowTarget` to every player every 0.5s via `Heartbeat`).

## Stands / abilities (combat)

**Flow**: client key press (`src/clientchar/StandAbilities.client.luau`, keys T/R/Z/X) → `StandAbilityFunction:InvokeServer(abilityId, state)` → `AbilityFunctionHandler.server.luau` → `AbilityHandler.luau` (resolves the equipped stand via `HeroGroups`, loads `ServerScriptService.BasicCombat.StandModules.<HeroGroup>.AbilityRegistry`, runs the shared Press/Hold/Toggle + cooldown state machine) → the stand's own module does server-authoritative work via shared utilities (`HitboxSpawner`, `CombatUtils`, `AnimationModule`) → server fires `ReplicatedStorage.Shared.Events.SpawnVfx:FireAllClients(payload)` → `src/client/VfxClientManager.client.luau` is the **single generic listener** that clones/plays the actual effect from `ReplicatedStorage.Effects.StandEffects`.

This confirms the "VFX doesn't exist on the server" design: the server never instantiates real effect Instances, only fires abstract descriptive payloads; the client owns all particle/visual assets.

**Adding a new stand** is folder-convention-based, not a single registration call: create `ServerScriptService.BasicCombat.StandModules.<Name>/` with an `AbilityRegistry.luau` (4 `AbilityTypes` + per-ability `Execute`) and a `<Name>.luau` implementation module using the shared combat utilities, then add entries to a handful of scattered lookup tables (`StandSummonSounds` in `StandUtils.luau`, `PUNCH_DAMAGE`/`BarrageCallSounds` in `BasicStandAttacks.luau`, `HeroGroups` if multi-form). **`StandRegistry.luau` looks like an abandoned attempt at a real central registry — it only lists 3 of 15+ stands and nothing actually uses it; don't treat it as authoritative.**

Shared plumbing everything routes through: `CombatUtils.luau` (stun/block/barrier/velocity/action-lock, damage reduction, target resolution — also scans `workspace.NPCs.EnemyNPCs` alongside players, so **NPCs take damage through the exact same path as players**, no separate NPC combat system), `HitboxSpawner.luau` (all melee/projectile/arc/guided/stationary/DoT damage application), `AnimationModule`, `SoundUtils`.

**Specialty abilities (Hamon/Vampirism/FengShui) are a parallel, independently-duplicated stack**, not a variant of the stand system: `src/server/BasicCombat/SpecailtyScripts/Handlers/AbilityHandler.luau` + `AbilityFunctionHandler.server.luau` reimplement ~90% of the stand handler's dispatch/cooldown logic separately (own cooldown tables, own remotes, own keybinds C/V/B/N, plus a Hamon-resource gate). If you fix a bug in one dispatch stack, check whether the other has the same bug.

**Note the typo**: the folder is `SpecailtyScripts` (misspelled), baked into paths throughout — don't "fix" it casually, it'll break requires everywhere; match existing spelling when adding to that tree.

Known dead code in this area: `StandModules/ThatHand/LastStand.server.luau` is explicitly marked outdated in its own header ("we now use a module based system"); several `src/shared/StandLocalScripts/**/*.client.luau` files still call old per-ability RemoteFunctions that the new generic `StandAbilityFunction` superseded.

## Movement speed

`CombatUtils.luau` is meant to be the single source of truth for a character's `Humanoid.WalkSpeed`, but **only part of the codebase actually goes through it** — treat this as a system with real gaps, not a clean central API, and read this before wiring up another ability that touches movement speed.

**The intended path**: `CombatUtils.GetMoveSpeed`/`SetMoveSpeed` hold a per-character *base* speed (`moveSpeedByCharacter`). `CombatUtils.ApplyMoveSpeedMultiplier` holds a separate per-character *transient multiplier* (`moveSpeedMultiplierByCharacter`; currently only used by `SetActionInProgress`'s 0.5x action-slow). `SlowingFieldRegistry.luau` (`src/server/BasicCombat/Managers/`) is a third, independent registry keyed by an arbitrary `sourceKey` string per caller (`SlowingField`, `Stun`, `Block`, etc.) whose entries multiply together (`GetFinalMultiplier`) — this is the best-designed piece of the system: stacking, additive sources, no collisions as long as keys are unique. `CombatUtils.UpdateMovement(character)` is the only function that combines all three (`base * multiplier * SlowingFieldRegistry.GetFinalMultiplier(character)`) and writes `humanoid.WalkSpeed` — the setters above call it for you.

**The reality**: most stand/ability modules bypass `UpdateMovement` and assign `humanoid.WalkSpeed` directly:
- `BlockModule.luau`, the slowing-field hitboxes in `HitboxSpawner.luau`, and the root/time-stop sequences in `StandModules/TheWorld/TheWorld.luau`, `StandModules/StarPurple/StarPurple.luau`, `StandModules/KaiserQueen/KaiserQueen.luau`, `StandModules/CrazedDiamond/CrazedDiamond.luau` all compute `base * SlowingFieldRegistry.GetFinalMultiplier(character)` (via the `CombatUtils.GetSlowMultiplier` wrapper) and assign `hum.WalkSpeed` themselves. This respects `SlowingFieldRegistry` but **silently drops the `moveSpeedMultiplierByCharacter` term** — any active `ApplyMoveSpeedMultiplier` value gets overwritten the next time one of these fires.
- `StandModules/Cream/Cream.luau`, `StandModules/StickyFingers/StickyFingers.luau`, `StandModules/TandemMode.luau`, and the `humanoid.WalkSpeed = 0` freeze moments inside `TheWorld`/`StarPurple`/`KaiserQueen` hardcode literal speed values (`0`, `4`, `16`) with no relation to `GetMoveSpeed` at all. If two such effects overlap, whichever assigns last wins with no stacking or priority; "restoring" speed means restoring the hardcoded `16`, not the character's real base speed, which breaks if base speed is ever race/upgrade-modified.
- `PilotModule.luau` restores speed via `humanoid.WalkSpeed = CombatUtils.GetMoveSpeed(character)` directly — like the above, this skips both `moveSpeedMultiplierByCharacter` and `SlowingFieldRegistry` on restore.
- `NPCController.luau` also writes `WalkSpeed` directly, but that module is dead/orphaned (see Stands and NPCs sections) — not a live conflict, just noise if you grep for `WalkSpeed`.

**Known bug**: `cleanupCharacter` in `CombatUtils.luau` clears `moveSpeedByCharacter`/`jumpHeightByCharacter`/etc. on death but never clears `moveSpeedMultiplierByCharacter` — a small per-character table leak (the dead `character` instance is kept alive as a table key).

**Rule for new abilities that modify movement speed**: go through `CombatUtils`, never assign `humanoid.WalkSpeed` directly.
- For a stacking slow/root, call `SlowingFieldRegistry.SetSlow(character, "<UniqueSourceKey>", multiplier)` / `ClearSlow` (multiplier `0 < x ≤ 1`; use `0` sparingly since it stacks multiplicatively with everything else, not as an override) then `CombatUtils.UpdateMovement(character)` — give it a source key specific to your ability, not a generic one another ability might reuse and unintentionally clear.
- For a genuine base-speed change (race/upgrade/buff), call `CombatUtils.SetMoveSpeed`.
- For a one-off transient multiplier outside the slow-field model, `CombatUtils.ApplyMoveSpeedMultiplier` exists but currently has exactly one caller (`SetActionInProgress`) and — per the gaps above — gets silently clobbered by several other systems; prefer `SlowingFieldRegistry` for anything that needs to coexist with block/stun/other slows.
- Every direct `humanoid.WalkSpeed = ...` assignment listed above is a pre-existing bypass to eventually clean up, not a pattern to copy.

**Proposed refactor (not yet done, cross-cutting — confirm scope before implementing)**: collapse `moveSpeedByCharacter`, `moveSpeedMultiplierByCharacter`, and `SlowingFieldRegistry` into one registry so `UpdateMovement` becomes the *only* place in the codebase that touches `humanoid.WalkSpeed`. Sketch: keep `SlowingFieldRegistry`'s keyed-multiplier-stack shape, but let an entry carry `{Override = 0}` instead of just `{Multiplier = x}` for hard stops/roots (an active override wins over the multiplied base, with a priority or last-writer rule for overlapping overrides — e.g. a stun should beat a self-inflicted charge-up root); fold `ApplyMoveSpeedMultiplier`'s single transient slot into the registry as another named source key (e.g. `"ActionInProgress"`) instead of a separate parallel table; keep `moveSpeedByCharacter`/`SetMoveSpeed` as the base-speed concept the registry multiplies against. Then replace every direct `humanoid.WalkSpeed = ...` in the modules listed above with the equivalent `SetSlow`/`ClearSlow`/`SetMoveSpeed` call, touching roughly: `BlockModule.luau`, `HitboxSpawner.luau`, `PilotModule.luau`, and the `TheWorld`/`StarPurple`/`KaiserQueen`/`CrazedDiamond`/`Cream`/`StickyFingers`/`TandemMode` stand modules.

## Quests

Definitions live in `src/server/DataSaving/QuestDefinitions.luau` — one large static table keyed by quest id, each with `Objectives` (Talk/Defeat/CheckPowers/Interact), `RewardXP`/`RewardCash`/`RewardItems`, `TurnInNpc`, `NextQuest` (chaining), `MinimumLevel`, `Repeatable`, `Manual`, and `Dialog` text. A generated block at the bottom auto-creates `Unlock_<NPC>` quests per NPC/repeatable pairing.

`QuestManager.luau` holds per-player in-memory active/completed quest state (deep-copied from definitions), advances progress on `DefeatedEnemy`/`InteractWithNPC`, and pushes state to the client via `QuestUpdatedEvent` (`ReplicatedStorage.QuestEvents`) after every change. `QuestSerializer.luau` converts that in-memory state to/from the data stored in the player's profile (`PlayerData.luau` calls it on load/save/slot-switch). `QuestArrowAssist.server.luau` runs a 0.5s heartbeat loop resolving each player's nearest incomplete-objective world position and pushes it for the client-side quest arrow.

**`RewardItems = "PurpleRokakaka"` (bare string) on the `DefeatDIO` quest is a likely real bug** — `CompleteQuest` iterates `RewardItems` with `ipairs`, which silently no-ops on a bare string instead of a table; every other quest uses the array form.

## Inventory

`InventoryManager.luau` holds a per-player in-memory array of `{Name, Amount}` stacks (server-authoritative, `InventorySerializer.luau` handles save/load and can rebuild Backpack `Tool`s from templates). `ItemUseManager.luau` auto-loads every module under `src/server/Rewards/Items/` into a name-keyed registry and dispatches `Use(player, itemName)` with per-item cooldowns — this **is** the item-definition source of truth for behavior. **`src/shared/Modules/ItemData.luau` is a separate, purely cosmetic (image/description) table keyed by the same item-name strings, with no enforced sync between the two** — adding an item module doesn't require (or get validated against) an `ItemData` entry, and vice versa.

## XP / progression

`XPSystem.luau` — in-memory per-`UserId` `{Level, XP, MaxXP, TalentPoints, AbilityPoints, UnlockedAbilities, XPBoostExpiry}`. XP-to-level formula: `100 + 20*(level-1)^2`, capped at level 120. `AddXP` applies any active purchased XP boost, handles multi-level-ups, awards badges via `BadgeHandler`, and fires update remotes. Triggered mainly by quest completion; also touched by admin chat codes. Note `SetStats`/`GetStats` (bulk) are effectively dead — normal load/save goes through per-field `SetField`/`GetField` in `PlayerData.luau`.

## NPCs / enemies

Data-driven: `EnemyDefinitions.luau` (flat table, tuning per enemy type — RespawnTime, aggro/chase radii, speeds; most entries share near-identical values). `EnemySpawner.luau` is an OOP per-spawn-point spawner (clone from `ReplicatedStorage.EnemyNPCs`, watches `Humanoid.Died` to respawn, Heartbeat leash check). `SpawnManager.server.luau` builds spawners per-folder and activates/deactivates them by player proximity every 5s — **has a duplicated variable-declaration bug** (`SpawnFolder`/`activeSpawners` declared twice, second shadows first; harmless but confusing) and a `print` that runs after an infinite loop (dead code, never executes). **`NPCController.luau` (a fairly complete pathfinding/aggro AI class) is required nowhere in the codebase — orphaned/dead**, actual NPC AI apparently lives in scripts baked into the NPC models themselves, not in this module.

Chests follow the same data-driven three-file pattern (`ChestDefinitions`/`ChestZoneDefinitions`/`ChestSpawner` + `ChestSpawnManager.server.luau`) and are noticeably cleaner, no equivalent bugs.

Objective minigames (`ControlPointModule.luau`, KOTH, 1v1) are mostly self-contained; `OneVsOneManager.server.luau` monkey-patches `OneVsOneModule.StartGame`/`EndGame` at runtime rather than the module exposing hooks — fragile, order-of-require-dependent, worth understanding before touching either file.

Two independent "home" concepts exist and are easy to conflate: `HomeManager.luau` (manual Innkeeper-registered home, used by `TeleportHandler`) vs. `SpawnHandler.server.luau`'s automatic nearest-death-position respawn — they don't share state.

## Ocean & Vehicles (newest systems, per git status — rougher edges)

`WaveModule.luau` is currently a stub (`GetHeight` returns a constant, no real wave motion). `VehicleController.client.luau` writes `SteerInput`/`ThrottleInput` attributes that `BoatController.luau` never reads (it uses native `VehicleSeat.SteerFloat`/`ThrottleFloat` instead) — the client script looks like leftover code from an earlier car-based system. `VehicleRaycastModule.luau` has collision-avoidance helpers built but not yet wired into `BoatController`. Treat these two systems as actively in-flux; verify current behavior in Studio before assuming any of the above is still accurate.

## Client architecture

Input scripts are thin: read `UserInputService`, `FireServer`/`InvokeServer`, no client-side prediction — server is authoritative throughout. `src/client/VfxClientManager.client.luau` is the single generic dispatcher for all visual effects (see Stands section). Overhead meters and damage numbers are pure event-driven listeners (no polling). `MusicAndLocalSounds.client.luau` is the one system that does poll, via a 0.5s Heartbeat proximity check.

**Triplicate/legacy shiftlock implementations exist simultaneously**: `src/client/ShiftLock.client.luau` and `src/clientchar/OldShiftLock.client.luau` are near-duplicate custom implementations (the "Old" one has its rotation logic commented out but still runs), while `src/client/RebindShiftlock.client.luau` takes a third, different approach (reprogramming Roblox's stock `MouseLockController` instead of reimplementing shiftlock). These can run concurrently and fight over `UserInputService.MouseBehavior`. If you touch shiftlock behavior, check all three files, not just the one that seems relevant.

## General conventions / rules to follow

- **Script suffix = execution context**, independent of folder — see Rojo layout section. Don't assume a file's behavior from its directory.
- **No central remote registry exists.** When adding a new RemoteEvent/RemoteFunction, prefer reusing an existing folder for the right domain and grep for existing similar remotes before creating a new one; there's no compiler to catch a typo'd remote name.
- **Server is authoritative everywhere**; client scripts should stay thin (input capture + Remote calls), with actual game-state changes validated and applied server-side.
- **Combat/ability additions**: use `HitboxSpawner`/`CombatUtils`/`AnimationModule` rather than writing new damage/hit-detection code — this is the established, heavily-used shared path.
- **Movement-speed changes**: go through `CombatUtils`/`SlowingFieldRegistry` (see Movement speed section) — never assign `humanoid.WalkSpeed` directly, even though a lot of existing stand code does.
- **This codebase has real duplication** (stand vs. specialty ability handlers, the three-way profile field-copy in `PlayerData.luau`, triplicate shiftlock). Before fixing a bug in one copy, check for and consider the sibling copy.
- **Known dead/orphaned modules** (safe to ignore as reference, risky to build on): `DataStoreManager.luau`, `PlayerProfile.luau`, `Test.server.luau`, `StandRegistry.luau`, `NPCController.luau`, `OldShiftLock.client.luau`, outdated per-ability `.server.luau`/`.client.luau` remote scripts under `StandModules/ThatHand` and `src/shared/StandLocalScripts/**`.

## Open documentation gaps / inconsistencies worth addressing (not fixed yet)

1. No shared module/constants file for RemoteEvent/RemoteFunction names — biggest single maintainability risk in the project.
2. `ItemData.luau` (cosmetic) and `ItemUseManager`'s item-module registry (behavior) are two unsynced sources of truth for "what items exist."
3. Three-way duplicated field-copy logic in `PlayerData.luau` (`LoadProfile`/`RemoveProfile`/`SafeSwitchSlot`) risks fields silently not persisting when the schema changes.
4. Stand ability dispatch (`StandModules/Handlers`) and specialty ability dispatch (`SpecailtyScripts/Handlers`) are ~90% duplicated independent implementations rather than a shared abstraction.
5. Likely real bug: `RewardItems = "PurpleRokakaka"` (bare string, not array) on the `DefeatDIO` quest in `QuestDefinitions.luau`.
6. `SpawnManager.server.luau` has duplicated variable declarations and dead code after an infinite loop.
7. Ocean (`WaveModule.luau`) and Vehicle (`VehicleController`/`BoatController` attribute mismatch) systems appear to be mid-development; don't treat their current state as final design.
8. Several dead/orphaned files listed above remain in the tree and could confuse future searches — consider removing once confirmed genuinely unused.
9. Movement speed has three parallel mutation paths (`moveSpeedByCharacter`, `moveSpeedMultiplierByCharacter`, `SlowingFieldRegistry`) plus numerous direct `humanoid.WalkSpeed` assignments that bypass all three — see Movement speed section for the affected files and a sketched consolidation.
